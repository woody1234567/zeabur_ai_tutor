# MCP 現況稽核報告

稽核日期：2026-06-20

## 範圍

本次檢查涵蓋：

- Nuxt 的 `@nuxtjs/mcp-toolkit` 設定
- `server/mcp/**` 下的 tools 與 resources
- Python AI service 的 MCP client 與啟動流程
- Docker Compose 中 Nuxt 與 AI service 的啟動關係
- MCP `/mcp` 端點的實際探索與基本呼叫

本文件只記錄目前發現的問題，尚未修改 MCP 實作。

## 問題清單

### P0：MCP 端點沒有驗證與授權

目前 `/mcp` 沒有自訂 handler middleware、使用者驗證或個別 definition 的 `enabled` guard。只要能存取端點，就能探索並呼叫所有 tools 與 resources。

受影響位置：

- `server/mcp/tools/recommend_materials.ts`
- `server/mcp/tools/search_problems.ts`
- `server/mcp/resources/classmaterial_list.ts`
- `server/mcp/resources/testbank_list.ts`

具體風險：

- `recommend_materials` 接受呼叫端提供的任意 `studentId`，沒有確認該身分是否屬於目前使用者。
- `search_problems` 回傳題目內容、選項、正確答案與解析。
- `classmaterial_list` 未取得學生身分時會回傳全系統教材。
- `testbank_list` 會列出整個題庫的 metadata。
- 若 `/mcp` 經公開網域暴露，外部呼叫者可直接繞過網站既有的 Better Auth 驗證。

建議：

1. 建立 `defineMcpHandler` middleware，驗證內部 service token 或使用者 session。
2. 採用 soft auth，成功時將身分寫入 `event.context`；不要從 middleware 回傳 `401`，避免 MCP client 誤觸 OAuth discovery。
3. 以 `enabled: event => Boolean(event.context.user)` 隱藏未授權 definitions。
4. 從驗證後的 context 取得 student ID，不接受呼叫端自行指定其他學生。
5. 若 MCP 只供 AI service 使用，將其限制於內部網路並使用 service-to-service credential。

### P0：AI service 啟動競態可能永久載入零個 tools（已改善，待部署驗收）

`packages/ai-service/src/tools/mcp_manager.py` 在 FastAPI 啟動時只初始化一次 MCP client。如果第一次 `get_tools()` 失敗，程式會將 `_tools` 設為空陣列，但 `_client` 仍保留。後續再次呼叫 `init_client()` 時，因 `_client` 已存在而直接返回，不會重新連線。

同時，`docker-compose.yml` 中：

- `web` 等待 `ai-service` 進入 started 狀態。
- `ai-service` 啟動時立即嘗試連線 `http://web:3000/mcp`。
- 此時 Nuxt web 可能尚未開始監聽。

可能結果：

1. AI service 第一次連線失敗。
2. `_tools` 被永久快取為空陣列。
3. Nuxt 稍後正常啟動，但 AI service 不再探索 MCP tools。
4. Agent 持續以零 tools 運作，直到 AI service 重啟。

已完成改善：

1. MCP discovery 加入可設定的 timeout、重試次數與 exponential backoff。
2. 只有成功完成 `get_tools()` 後才提交 `_client` 與 `_tools` 狀態。
3. Discovery 失敗時保持未初始化狀態，後續聊天請求會再次嘗試連線，不需重啟 process。
4. 使用 async lock，避免多個請求同時重複初始化 MCP client。
5. Nuxt web 新增 `/mcp` `tools/list` health check。
6. 主 `docker-compose.yml` 移除 `web -> ai-service` 依賴，改為 `ai-service -> healthy web`。
7. 主 Compose 固定使用容器服務位址 `http://web:3000/mcp`，避免 host 的 localhost 設定在容器內指向錯誤服務。
8. 新增單元測試，驗證重試後成功、失敗後可恢復及併發初始化三種情境。

可設定環境變數：

- `MCP_CONNECT_MAX_ATTEMPTS`，預設 `8`
- `MCP_CONNECT_INITIAL_DELAY_SECONDS`，預設 `0.5`
- `MCP_CONNECT_MAX_DELAY_SECONDS`，預設 `5`
- `MCP_CONNECT_TIMEOUT_SECONDS`，預設 `5`

尚待部署環境驗收：

- 同時冷啟動 Nuxt、PostgreSQL 與 AI service，確認 AI service 最終載入 3 個 tools。
- 暫時延遲 Nuxt 啟動，確認 retry/backoff 能自動恢復。
- Nuxt 已啟動後重新啟動 AI service，確認 health dependency 與 discovery 正常。

### P1：MCP 錯誤回應洩漏內部 SQL

`search_problems` 與 `recommend_materials` 直接將捕捉到的 `error.message` 放入 MCP response。

實際測試 `search_problems` 時，回應包含完整 SQL、欄位名稱與 query params。這會向 MCP client 暴露資料庫結構與內部實作。

建議：

- 在伺服器端記錄完整錯誤。
- 對 MCP client 回傳固定且經過清理的錯誤訊息。
- 使用 `throw createError({ statusCode, message })` 交由 toolkit 轉換成 `isError` response。
- 不要將原始 exception message、SQL 或 credentials 傳回 client。

### P1：Resources 無授權、分頁與資料量限制

`classmaterial_list` 與 `testbank_list` 都可能一次讀取完整資料表，並將結果序列化成單一 MCP resource response。

影響：

- 資料量增加後產生巨大 JSON payload。
- 增加 DB、記憶體、網路與模型 context 成本。
- MCP client 可能超過 response 或 context 限制。
- 所有使用者資料混在同一個 resource，無法落實資料隔離。

建議：

- 使用 `ResourceTemplate` 提供 page、limit 或 cursor。
- 設定合理的單頁上限。
- 依驗證後的使用者或 classroom context 過濾資料。
- 僅回傳任務所需欄位，避免完整資料傾印。

### P1：`recommend_materials` 存在 IDOR 風險

`recommend_materials` 的 `studentId` 完全由 MCP 呼叫端提供。只要知道或猜到另一位學生的 ID，就可能查詢該學生被分享的教材、班級與教材 URL。

建議移除公開的 `studentId` input，改從 MCP middleware 建立的身分 context 取得。若教師或管理員需要代查，必須加入明確角色與資源授權判斷。

### P2：舊的 AI service wrapper 與 MCP schema 不一致

`packages/ai-service/src/graph/nodes.py` 的 `search_problems_tool()` 傳入：

```python
{"query": query, "limit": 5}
```

但 `search_problems` MCP schema 只接受：

- `title`
- `source`
- `hashtag`

實際測試確認，多餘欄位會被忽略，結果退化成無條件查詢前 10 題，而不是依使用者 query 搜尋。

目前主要 workflow 使用 LangGraph agent 直接載入 MCP tools，沒有呼叫這組 wrapper；但保留失效程式碼會造成未來誤用。

建議：

- 若不再使用，刪除舊 wrapper 與 mock action nodes。
- 若仍需使用，建立明確的 query-to-schema mapping 並加入契約測試。

### P2：Tool schema 約束不足

目前 `recommend_materials.limit` 只宣告為 `z.number()`，沒有整數、正數與最大值限制。

影響：

- 可傳入負數、小數或極大數值。
- 可能造成資料庫錯誤或過量查詢。

建議改為類似：

```ts
z.number().int().min(1).max(50).default(5)
```

其他文字欄位也應加入合理的長度限制。

### P2：缺少 MCP annotations 與 input examples

現有 tools 沒有提供：

- `readOnlyHint`
- `destructiveHint`
- `idempotentHint`
- `openWorldHint`
- `inputExamples`

這些 metadata 能協助 MCP client 與模型理解工具是否唯讀、是否影響外部狀態，以及如何正確呼叫。

目前兩個正式 tools 都是資料庫唯讀操作，至少應標註：

```ts
annotations: {
  readOnlyHint: true,
  destructiveHint: false,
  idempotentHint: true,
  openWorldHint: false,
}
```

### P2：Tool handler 使用不必要的手動 response 與 `any`

現有 handlers 手動建立完整 `content` response，且 `recommend_materials` 使用 `args: any`。這會弱化 Zod schema 帶來的型別推導，也增加 response 格式出錯的機會。

`@nuxtjs/mcp-toolkit` 可直接回傳 string、object 或 array，錯誤則直接 throw。建議改用直接回傳並移除 `any`。

### P2：Production 暴露測試工具

`server/mcp/tools/test.ts` 會在所有環境被自動探索並公開。

雖然目前只有 echo 功能，但它：

- 增加無實際用途的 production capability。
- 讓模型可能選到不相關工具。
- 容易在未來測試修改後意外暴露更多行為。

建議刪除，或透過 `enabled` 僅在 development 環境公開。

### P3：存在未使用的 YAML 定義

`server/mcp/definitions/*.yaml` 與 TypeScript definitions 重複，但 `@nuxtjs/mcp-toolkit` 實際自動探索的是：

- `server/mcp/tools/*.ts`
- `server/mcp/resources/*.ts`
- `server/mcp/prompts/*.ts`

目前沒有程式讀取這些 YAML，因此它們不是 MCP server 的實際契約。雙重定義容易隨時間產生漂移，使開發者誤判真正暴露的 schema。

建議選擇單一 source of truth；若沒有外部 generator 使用 YAML，應移除或清楚註明用途。

### P3：缺少 MCP 自動化測試

目前沒有發現針對以下行為的自動測試：

- tools/resources discovery
- 未授權呼叫拒絕
- 使用者資料隔離
- tool schema validation
- SQL error sanitization
- AI service 啟動重試
- MCP tool selection eval

至少應加入 MCP JSON-RPC smoke tests，以及針對安全邊界與 AI service retry 的測試。

## 建議修復順序

1. 加入 MCP authentication、authorization 與資料隔離。
2. 修正 AI service MCP 初始化競態，加入 retry/backoff 與 readiness check。
3. 清理錯誤 response，禁止洩漏 SQL 與內部 exception。
4. 將 resources 改成有授權的分頁查詢。
5. 強化 Zod schema、annotations 與 input examples。
6. 移除 production test tool、失效 wrappers 與未使用 YAML。
7. 補上 MCP integration tests 與 tool-selection evals。

## 驗收條件

- 未授權 client 無法探索或讀取受保護的 tools/resources。
- 學生只能取得自己有權限存取的題目與教材。
- AI service 即使比 Nuxt 早啟動，也會在 Nuxt ready 後自動載入 tools。
- MCP errors 不包含 SQL、stack trace、credentials 或內部連線資訊。
- 所有 list resources 都有分頁與最大筆數限制。
- Production 不公開 `test` tool。
- CI 可執行 MCP discovery、authorization、schema 與 retry 測試。
